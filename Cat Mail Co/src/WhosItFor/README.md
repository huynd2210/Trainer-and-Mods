# Who's It For?

In the unmodified game a customer will often describe their parcel and never say who it is for â€” "It's a small box.", "I warn you, it's a heavy package." â€” leaving you to guess between similar boxes. This mod makes sure every request also names the customer.

**Nothing is removed.** The customer still says everything they said before â€” size, weight, ribbons, stickers, storage constraints â€” you just get the name as well.

## What it changes

A customer request is not a single string. The game picks the parcel first, then assembles a list of `DialogueData` lines describing it: a greeting, one or more clue lines, and optional `Link` connectors ("By the way,", "Also,") joining them. `CustomerDialogueManager.GetRequestDialogue` builds that list.

This mod adds one postfix to that method:

1. If the request already contains a `PersonName` line, it is left completely untouched.
2. If it does not, the mod asks the game for one via `CustomerDialogueManager.GetDialogue(DialogueType.PersonName, customer, mood)` and inserts it after the greeting.

### Why it asks the game for the line

Name lines come in two flavours: `MatchName` ("My name is $NAME$ $SURNAME$.") claims the full name matches the label, while `MatchSurname` ("Look for $SURNAME$.") only claims the surname does. Parcels carry a `CustomerNameIndex`, a `CustomerSurnameIndex` **and** a separate `CustomerLastNameInitial`, so a label does not always spell out both parts in full.

Picking the wrong flavour would produce a clue that is actively misleading, so the mod does not choose one. It calls the game's own `GetDialogue` helper â€” the same one the game uses (`CallerCount = 2`, so it is definitely present in the build) â€” and inserts whatever that returns, logging the category it picked.

### It cannot make a request harder

`RequestCheckResult` is `{ Valid, WrongParcel, NoParcels }` â€” there is no "wrong size" or "wrong name" outcome, so correctness is identity-based: it is that one specific parcel or it isn't. Dialogue is only a hint for the player, never the pass condition.

Combined with the fact that this mod only ever *adds* a line, the original clues still fully determine the answer. Worst case the added line is redundant.

## Configuration

`BepInEx/config/com.catmailco.whositfor.cfg`:

| Setting | Default | Effect |
|---|---|---|
| `AddCustomerName` | `true` | Add the customer's name to requests that only describe the parcel. |
| `VerboseLogging` | `true` | Log the make-up of every request and every name added. |

## Logging

With `VerboseLogging` on, `BepInEx/LogOutput.log` gets one line per request:

```
request already names the customer, left as-is :: [name+description] Hello | PersonName | Link | Size
added customer name [ClientDialogues2/PersonName_1 / MatchSurname] :: [description only] Hello | Size  ->  [name+description] Hello | PersonName | Size
```

The `[verdict]` tag also shows whether the vanilla game mixes clue types at all: if requests reported as *already named* show `[name+description]`, the two are not mutually exclusive.

Warnings worth watching for:

- `No name line available for this customer` â€” `GetDialogue` returned nothing; the request was left alone.
- `GetDialogue returned a <type> line instead of PersonName` â€” unexpected selection, insertion skipped.

Both fail safe: the request keeps its vanilla clues.

## Multiplayer

Customer dialogue is generated by the session host and synced to clients, so install this on the **host**. Installing it on every player is safest.

## Dialogue reference

`CustomerDialogue.md` and `CustomerDialogue.csv` list every customer line in the game with its `DialogueType`, `DialogueCategory`, `DialogueAge` and `DialogueMood`. `extract_dialogue.py` regenerates them from `CatMailCo_Data/resources.assets`, and `dialogue.json` holds the full extraction including all 13 translations.

## Build

Run `build.ps1` from this directory after BepInEx has generated the IL2CPP interop assemblies.

The installed plugin is `BepInEx/plugins/WhosItFor/WhosItFor.dll`.
